# VATE v0.6.0 Discussion-Draft Pre-Release Notes

`v0.6.0` adds tools for a receiving application to choose which records it
requires, retain the original bytes and earlier assessments, and reassess when
evidence arrives or its conditions change. A standalone runtime-key revocation
sample follows an existing admission through provider acceptance and observed
file effects. These examples extend the usable reference paths while retaining
the AL2 admission profile v0.3.

Obtain the complete source from the
[v0.6.0 GitHub release](https://github.com/Poke-nushi/Verifiable-Agent-Trust-Envelope/releases/tag/v0.6.0),
then choose one of the paths below. Each linked README lists its prerequisites
and commands. The verified archive is available at
[10.5281/zenodo.23626404](https://doi.org/10.5281/zenodo.23626404).

## Choose a Review Path

- [Required Record Review](../../reference/required-records/README.md) starts
  from a receiver-selected set of operations or known attempts. An operation
  omitted from a submission still appears in the report; missing records,
  pending deadlines and incomplete collection remain distinct. The local
  contract supports the existing S3 and file-set operation contexts.
- [Recipient Inbox](../../reference/recipient-inbox/README.md) stores raw
  originals, fixed review inputs and successive assessments in SQLite. Its
  [package intake example](../../reference/recipient-inbox/PACKAGE-INTAKE.md)
  derives collection status from actual file reads and registration. Exported
  history can be reassessed with an explicitly selected evaluator.
- [MUSUBI set2 recipient sample](../../reference/musubi-set2-receiving-sample/README.md)
  connects published records to receiver-selected requests and evidence
  requirements. Start with the published settlement records, then add audits
  for work items A and C or signed work-assessment records from another verifier;
  retain both the native result and the later assessments. Repeated intake
  reuses identical named originals, and saved-output recovery does not rerun
  the native evaluator.
- [Post-Admission Runtime-Key Revocation Sample](../../reference/post-admission-revocation-sample/README.md)
  checks signed status before a local provider accepts a two-file operation.
  Eight scenarios distinguish refusal, completed effects and an unresolved
  partial result. Query, export and a separate reader preserve the original
  admission and acceptance history. The complete sample folder runs separately
  from a VATE checkout with disposable test keys and a fixed clock.

Each README provides environment preparation, commands and expected results.
The core receiving paths use the repository's existing Python validation
dependencies. The revocation sample requires Python 3.11–3.14 and an existing
OpenSSL executable on Linux or macOS. Full native MUSUBI replay requires macOS;
its Linux checks cover parsing, signatures, binding, storage and recovery,
with saved native output used in the receiver binding tests.

## Published Experiment Records

The [Horizon Shield #51 replay record](../interop/horizon51-set2-replay/README.md)
preserves the selected signatures, hashes, native replay and header-view
reassessment. The [A/C audit receiving record](../interop/horizon51-set2-audit-receiving/README.md)
checks the published audit/dataset bytes and their selected execution links.
The [foreign acceptance validation](../../reference/musubi-set2-receiving-sample/ACCEPTANCE-VALIDATION.md)
includes a separate B-audit follow-up.

Under the opt-in `hs51-war-bindings-v0-1` contract, a receiver selects the
verifier and timestamp trust roots. Verification binds the signed work verdict
to the selected request, execution and criteria. A verified `fail` is a valid
record of a failed work assessment. It does not become a verifier error or
overwrite the native MUSUBI `accepted: null`. The required-evidence result can
remain `partial`; audit-byte linkage does not establish actual dataset use.

These are fixed-source experiment and interoperability records. They do not
report new external implementations passing the VATE conformance corpus.
Historical source pins, contributor reports and comparison outcomes remain
attached to their original records.

## Storage and Recovery

The MUSUBI sample reuses retained originals across acquisition manifests while
preserving provenance and past assessments. A capacity failure rolls back the
whole new retention batch; the Inbox's existing 256-entry limit is unchanged.
Recovery reconstructs output from the saved run. A saved evaluator error stays
an error after recovery.

The revocation sample keeps the original `allow` separate from current key
status, provider acceptance and effects. Revocation committed before acceptance
prevents that acceptance; later revocation does not erase an accepted operation
or undo its effects. Its evidence reader checks an export against separately
supplied expected keys and context, rather than trusting the export's own
selection as authority.

The profile, schemas and corpus are unchanged from `v0.5.0`. The added
demonstration scenarios and local API contracts are separate from that corpus.
Existing experiment source pins are retained; selecting this release does not
silently substitute a new evaluator for a pinned historical one.

The [release gate](../release-gate-v0.6.0.md) records the source checks and
archive sequence. CI includes Linux Python 3.11–3.14 for the new receiving and
revocation paths, macOS checks, and checkout/source-archive validation. The
broader execution examples retain their existing Python matrix. Native MUSUBI
replay remains macOS-only. Development maintenance also updates the pinned
Vitest and fast-uri versions and validates workflow syntax with actionlint.

VATE remains an Apache-2.0 discussion draft, not production-ready. These local
contracts and fixed-source checks do not establish complete JOSE/PKI
validation, independent real-world identity or history completeness, general
compatibility, certification or production approval. Third-party materials
retain the licenses and provenance described in their source records.
