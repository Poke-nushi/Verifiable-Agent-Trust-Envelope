# VATE v0.7.0 — Checking what an agent was allowed to do

An agent requests a USD 120 spending limit for a USD 24.50 purchase. The verifier
lowers the limit to USD 25 and records that decision in a receipt. How can the
recipient check that the limit was the only thing that changed?

With v0.7.0, a recipient who has the admission request and both versions of the
purchase instructions can recompute their hashes and compare them with the
receipt. In this example the purchase amount stays at USD 24.50. A synthetic
post-execution receipt links back to the admission receipt and the approved
instructions. No purchase is made.

VATE is an Apache-2.0 specification draft for recording decisions about agent
actions and linking those decisions to evidence of what happened afterward.
This is a discussion-draft pre-release.

## Try the purchase example

From the root of the `v0.7.0` source tree, run this command with Python 3.10 or
later on macOS or Linux.

```bash
python3 reference/request-binding/example.py check \
  --bundle reference/request-binding/examples/purchase-cap \
  --expected-admission-request reference/request-binding/examples/purchase-cap/admission-request.json
```

Look for `"binding_requirement_met": true` inside `request_binding`. It means
the receipt agrees with the selected admission request and the original and
approved purchase instructions. This example uses an unsigned receipt and
reports `"execution_observed": false`. Authenticating the issuer and observing
a purchase each require separate evidence. The example supplies a known request.
In an integration, the recipient selects the expected request from its own
records. [Purchase example guide](../../reference/request-binding/README.md)

## Breaking change for Python callers

Replace `verifier.admit(request)` with
`result = verifier.admit(admission_bytes, original=original_bytes)`. Pass the
raw UTF-8 JSON bytes of the admission request and the original purchase operation.
The old dictionary-only call raises `TypeError` without issuing a receipt.
Use `json.loads(result.receipt)` to read the final decision.

The default Python entry accepts the `vate-purchase-cap-request-v1` operation
with exactly one `local_policy` reference matching the configured policy.
Other operation or evidence types raise `ValueError` and require a validated
adapter. Python and TypeScript both include the recipient check. The TypeScript
code is available in the repository's unpublished workspace package. Receipt
issuance and the optional pre-dispatch check are implemented in Python.
[Python migration guide](../../reference/request-binding/MIGRATION.md) and
[TypeScript example](../../packages/vate-core-ts/README.md#check-request-binding)

At release, npm flagged picomatch, which Vitest uses to select test files.
GitHub later [withdrew the advisory](https://github.com/advisories/GHSA-fc5q-39xc-vjpf).
Both the full and production-only npm audits then reported zero findings with
the original v0.7.0 lockfile.
The Python purchase example runs without these tools.
[Audit results for the release lockfile](../release-gate-v0.7.0.md#typescript-test-dependencies)

## When permission changes

Before handing work to the application, the optional Python integration
rechecks permission against its latest installed, signed authority snapshot.
A revocation installed since admission can stop the handoff. Recorded dispatch
attempts survive a process restart. Even when an attempt's outcome is unknown,
the integration blocks a second dispatch.

A separate example migrates one stopped deployment built from commit
`6758476` to a new program, authority key and local stores on the same host.
Earlier receipts retain their original bytes, previously attempted operations
stay blocked, and new work needs a fresh authority update and admission.
[Authority updates](../../reference/authority-updates/README.md) and
[planned migration](../../reference/planned-migration/README.md)

## What the tests cover

The AL2 v0.3 fixture set still contains 76 cases. Its digest changed, so
results for v0.6.0 remain tied to that earlier snapshot. The 76 cases check
declared receipt fields and links. They do not recompute the purchase hashes
from the instructions, and `request.input_hash` and
`attenuation.original_request_hash` can differ.

A separate four-case set requires that recomputation. It covers an allowed
purchase, a lowered limit, a lowered limit that requires a new permit before
execution, and a denial. Even a denied purchase can pass the binding check when
the receipt accurately describes that denial. The `run` and `compare` reports
identify which cases require the check and how many satisfy it.
[Receipt binding rules](../receipt-model-v0.3.md#request-to-admission-to-effect-binding-invariant)

For file operations, the [handoff example](../../reference/runtime-handoff-sample/README.md)
shows how a recipient assesses complete, partial or unobserved effects. The
[changelog](../../CHANGELOG.md#v070) lists receiving examples for WAR,
Restoration RB, Border relay, UIBC and x402 MCP, with links and evidence details
in the [repository guide](../../README.md#reviewer-entry-points).

The [release verification record](../release-gate-v0.7.0.md) identifies the
tested source and fixture sets. The reference implementations are intended for
technical review. [Known gaps](../known-gaps.md)
